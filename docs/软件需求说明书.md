## 1. 引言

### 1.1 选题背景

高校宿舍管理中，照明、空调、窗帘、加湿等设备的开关依赖人工操作，既存在能源浪费，也难以对"无人时关灯""高温时开空调"等场景做出及时响应。本选题面向**智能宿舍自动化管理**，让学生以"规则编排"的方式自行设计联动方案——当满足条件时自动执行设备动作，并通过模拟环境检验效果。

### 1.2 选题功能概述

本应用提供一套**不依赖真实硬件与云平台**的联动规则编排与模拟验证环境：

- 学生可设计"**满足条件时执行设备动作**"的自动联动方案（规则）；
- 可通过**模拟环境数据**检验联动规则是否按预期触发；
- 支持**新增、修改、启停规则**，含一条由**两个条件共同决定**的规则；
- 规则引擎**根据实际输入计算触发结果**，并记录触发条件、设备变化与执行顺序；
- 对相互冲突的控制提供**明确的执行顺序与优先级**处理；
- 支持**多组环境场景**的模拟演练；
- **保存设备设置、规则与执行记录**，退出重启后仍可恢复。

### 1.3 术语与缩写

| 术语 | 说明 |
| --- | --- |
| 规则（Rule） | 由条件与动作组成的联动逻辑单元 |
| 条件（Condition） | 对环境数据（温度/湿度/光照/是否有人）的判断表达式 |
| 动作（Action） | 对某个设备执行的开关或数值设置 |
| 优先级（Priority） | 规则间冲突时决定执行先后顺序的数值，越小越先执行 |
| 场景（Scene） | 一组预设环境数据的组合，用于演练 |
| 执行批次（ExecutionBatch） | 一次环境变化引发所有规则按序执行产生的日志快照 |

## 2. 功能需求

### 2.1 功能模块划分

本应用划分为五个功能模块：

| 模块 | 功能 | 对应页面 |
| --- | --- | --- |
| M1 设备控制 | 展示 4 类设备，支持开关与数值调节 | `DevicePage` |
| M2 模拟环境 | 调节温度/湿度/光照/是否有人，触发联动 | `EnvPage` |
| M3 规则管理 | 规则的增删改查与启停 | `RulePage` |
| M4 场景演练 | 载入预设场景，观察联动效果 | `ScenePage` |
| M5 执行日志 | 查看触发条件、设备变化、执行顺序与冲突 | `LogPage` |

### 2.2 详细功能需求

**FR-1 设备控制**
- 至少 4 类可控制设备：灯、空调、窗帘、加湿器。
- 每类设备支持开关切换；灯（亮度）、空调（温度）、窗帘（开合度）支持数值调节。
- 设备状态变化实时保存并同步 UI。

**FR-2 模拟环境**
- 至少 3 项可调整环境数据：温度、湿度、光照强度，另含"是否有人"布尔量。
- 环境数据变化后实时触发规则引擎重新计算。

**FR-3 规则管理**
- 支持新增、修改、启停、删除规则。
- 内置 ≥4 条规则，其中至少 1 条由**两个条件共同决定**（逻辑 AND）。
- 规则由条件（可多个）、逻辑关系（AND/OR）、动作、优先级构成。

**FR-3.1 双条件规则（核心验收点）**
- 规则的 `conditions` 为条件数组，`logic` 字段决定多条件组合方式：`AND`（所有条件同时满足才触发）或 `OR`（任一条件满足即触发）。
- 内置双条件规则示例：「高温且有人开空调」—— 当 `温度 > 28` **且** `有人` 两个条件同时满足时，自动开启空调并设为 24℃。
- 验证方式：温度 28℃ 且无人 → 不触发；温度 29℃ 且有人 → 触发。
- 该行为由单元测试 `evaluateRule_double_condition_and` 用例覆盖。

**FR-4 规则引擎**
- 根据**实际输入的环境数据**计算每条规则的触发结果。
- 记录触发条件、设备变化、执行顺序。
- 多规则命中同一设备时，按优先级裁决执行顺序并记录冲突。

**FR-5 场景演练**
- 支持 ≥2 组环境场景一键载入。

**FR-6 数据持久化**
- 设备设置、规则、执行记录持久化，关闭进程后重开可恢复。

### 2.3 非功能需求

| 编号 | 需求 |
| --- | --- |
| NFR-1 | 采用 ArkTS + ArkUI 声明式开发，DevEco Studio 工程 |
| NFR-2 | 核心业务逻辑（规则求值、冲突裁决）实现为纯函数，可单元测试 |
| NFR-3 | 采用 `@State` / `@Prop` 状态管理与 `emitter` 事件通信（跨页面联动） |
| NFR-4 | 规则求值、双条件、冲突优先级、全运算符、多动作具备自动化单元测试覆盖 |

## 3. 数据模型设计

### 3.1 设备（Device）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 设备唯一标识 |
| name | string | 设备名称 |
| type | DeviceType | 枚举：light / aircon / curtain / humidifier |
| on | boolean | 开关状态 |
| value | number | 附加数值（亮度/温度/开合度） |
| lastRuleId | string | 最近操控该设备的规则 id |

### 3.2 环境数据（EnvState）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| temperature | number | 温度（℃） |
| humidity | number | 湿度（%） |
| illuminance | number | 光照强度（lux） |
| occupancy | boolean | 是否有人 |

### 3.3 规则（Rule）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 规则唯一标识 |
| name | string | 规则名称 |
| enabled | boolean | 是否启用 |
| conditions | Condition[] | 条件列表（可多个） |
| logic | Logic | AND / OR |
| actions | Action[] | 动作列表 |
| priority | number | 优先级（越小越先执行） |

**条件 Condition**：`{ field: 环境字段, operator: 比较符, value: 数值 }`
**动作 Action**：`{ deviceId, deviceType, on, setValue? }`

### 3.4 执行日志（LogEntry / ExecutionBatch）

| 字段 | 说明 |
| --- | --- |
| id | 日志唯一标识 |
| timestamp | 触发时间 |
| ruleId / ruleName | 触发规则 |
| triggerCondition | 触发条件描述 |
| order | 执行顺序序号 |
| deviceChanges | 设备变化描述列表 |
| conflictNote | 冲突说明 |

### 3.5 场景（Scene）

| 字段 | 说明 |
| --- | --- |
| id / name / description | 场景标识与说明 |
| env | 场景对应的环境数据快照 |

## 4. 接口设计

### 4.1 模块接口（组内约定）

模块间通过 **`AppState` 全局单例 + 事件总线** 通信，各模块对外接口如下：

**规则引擎（`engine/RuleEngine`）**

```
class RuleEngine {
  setRules(rules: Rule[]): void
  setDevices(devices: Device[]): void
  run(env: EnvState, now?: number): ExecutionBatch   // 核心入口
}

function evaluateRule(rule: Rule, env: EnvState): RuleEvaluation  // 单规则求值
function evaluateCondition(condition: Condition, env: EnvState): boolean
```

**持久化（`store/StoreManager`）**

```
class StoreManager {
  static getInstance(): StoreManager
  init(context: UIAbilityContext): Promise<void>
  saveDevices(devices: Device[]): Promise<void>
  loadDevices(): Promise<Device[]>
  saveEnv(env: EnvState): Promise<void>
  loadEnv(): Promise<EnvState>
  saveRules(rules: Rule[]): Promise<void>
  loadRules(): Promise<Rule[]>
  appendLog(batch: ExecutionBatch): Promise<void>
  loadLogs(): Promise<LogEntry[]>
  clearLogs(): Promise<void>
}
```

**状态管理（`store/AppState`）**

```
class AppState {
  restore(): Promise<void>
  setTemperature(value: number): Promise<void>
  setHumidity(value: number): Promise<void>
  setIlluminance(value: number): Promise<void>
  setOccupancy(value: boolean): Promise<void>
  runEngine(): Promise<void>
  toggleDevice(id: string): Promise<void>
  setDeviceValue(id: string, value: number): Promise<void>
  addRule(rule: Rule): Promise<void>
  updateRule(rule: Rule): Promise<void>
  deleteRule(id: string): Promise<void>
  toggleRule(id: string): Promise<void>
  loadScene(sceneId: string): Promise<void>
  clearLogs(): Promise<void>
}
```

> 说明：环境数据采用 4 个独立 setter（`setTemperature` 等）而非 `Partial<EnvState>` 合并更新，
> 以规避 ArkTS 对 `Partial` 工具类型的限制，每个 setter 内部统一走 `applyEnvChange()` 完成
> 「保存环境 → 广播事件 → 重算规则引擎」的闭环。

**事件通信（`common/EventBus`）**

```
enum EventType { ENV_CHANGED, DEVICE_CHANGED, RULE_CHANGED, LOG_UPDATED, SCENE_LOADED }
function emit(type: EventType): void
function onEvent(callback: (data: EventData) => void): () => void   // 返回取消订阅函数
```

### 4.2 数据存储接口

| 存储 | 技术 | 内容 |
| --- | --- | --- |
| Preferences（`dorm_automation`） | `@ohos.data.preferences` | 设备开关与数值状态、环境数据 |
| RDB（`dorm.db`） | `@ohos.data.relationalStore` | `rules` 表、`logs` 表 |

**rules 表结构**：`id, name, enabled, conditions, logic, actions, priority`
**logs 表结构**：`id, batch_id, timestamp, rule_id, rule_name, trigger_condition, order_no, device_changes, conflict_note`

## 6. 测试方案

### 6.1 单元测试

使用 `@ohos/hypium`，覆盖以下用例：

| 测试文件 | 覆盖内容 |
| --- | --- |
| `ConditionEvaluator.test.ets` | 比较运算符（GT/GTE/LT/LTE/EQ/NEQ）、布尔字段读取、单条件求值、边界值不触发 |
| `RuleEngine.test.ets` | 双条件 AND、OR 逻辑、执行顺序、冲突优先级、同优先级按 id 排序、只触发满足条件的规则、多动作规则、停用规则不触发 |
| `DefaultData.test.ets` | 4 类设备、≥4 规则含双条件、≥2 场景 |

### 6.2 功能测试（人工）

| 场景 | 操作 | 预期 |
| --- | --- | --- |
| 联动触发 | 温度调至 29 且"有人" | 空调开启并写入日志 |
| 冲突裁决 | 温度调至 31 且"有人" | 日志出现两条规则，含冲突标记 |
| 场景演练 | 载入"夏日午后" | 环境数据变化并触发对应设备 |
| 持久化恢复 | 修改设备/规则后杀进程重开 | 状态完整恢复 |
| 规则管理 | 新增/编辑/启停/删除规则 | 列表与引擎实时同步 |

### 6.3 验收方式

- 功能验收：对照第 2 节功能需求逐条演示。
- 代码验收：规则求值与冲突裁决为纯函数，`ohosTest` 单测可运行通过。
- 数据验收：关闭应用进程后重新打开，设备设置、规则、执行记录均恢复。
- 文档验收：《软件需求说明书》保存于仓库 `docs/` 目录。
